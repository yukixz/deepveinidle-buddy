# 独立制造工具：Shadow DOM、收藏订单与游戏面板样式

日期：2026-10-22。本文件保留实施前调研与方案依据，其中“尚未实施／未验证”指调研时点；现行实现与本次验证见[实施报告](implementation.md)。不以此草案代替当前设计。当前基线见[当前状态](../docs/status.md)，现行规则见[制造](../docs/reference/crafting.md)、[收藏](../docs/reference/collection.md)及[技术方案](../docs/reference/technical.md)。

## 已确认范围与建议结论

用户已确认的目标：

- 制造拆分为独立项目，通过 userscript 在游戏内运行打包应用，以 Shadow DOM 承载面板，并同步游戏数据。
- 将当前收藏页面重构为制造页的订单模式，纳入配方选择面板。
- **同一订单可以混合制造配方与收藏目标，共用执行计划。**
- **样式优先保持与游戏内面板一致。**

建议采用一个 userscript 发布产物，包含早期只读捕获器、应用 UI、局部样式、独立打包的计算 Worker 源码和 GM 平台适配器。运行时不依赖实验室在线页面；新项目自身可构建、测试和发布。原先优先考虑 iframe 的建议由本方案替代。

主要新增工作不是画一个面板，而是把现有全局 DOM 与 localStorage 依赖改为实例内依赖，扩展订单项类型，并把收藏进度与制造次数分开计算。Shadow DOM 可行性尚需真实脚本管理器验证，不能据此认定 Worker、注入时机和所有游戏快捷键均兼容。

本轮仅整理调研报告和索引；不创建新项目、不重构现有功能、不删除旧入口、不部署。跨模块实现前，须按 AGENTS.md 确认具体修改清单，再先更新相应设计文件。

## Shadow DOM 运行与打包

```text
userscript（document-start）
  ├─ 先安装同源 WebSocket 只读捕获器 → 最新状态内存缓存
  ├─ DOM 可用后挂载唯一宿主元素 → Shadow Root → 应用实例
  │    ├─ 配方选择：制造 / 收藏
  │    ├─ 当前订单与订单管理
  │    └─ 执行计划、材料、价格及同步状态
  ├─ GM 存储 / 公开行情 / 剪贴板适配器
  └─ 内嵌 Worker 源码 → Blob Worker → 带版本的计算结果
```

### 发布产物与运行边界

建议将 UI 打包为本地闭包，将计算 Worker 依赖打包成无外部 import 的单独代码文本，再一起装入 `.user.js`。先装捕获钩子，后启动较重的应用初始化。保留安装版本、数据协议和来源标识；升级由脚本管理器完成，不在运行中从可变远程地址下载并 eval 应用。

不要给捕获启动增加大型远程 `@require` 前置依赖。Tampermonkey 明确说明远程依赖可能推迟 document-start 脚本执行。[官方注入时机说明](https://www.tampermonkey.net/documentation.php?q=run_at)

现有 `new Worker(new URL(..., import.meta.url), {type:'module'})` 不能原样搬到内嵌 userscript。建议测试完整打包的 Blob Worker；不依赖远程 Worker 路径。浏览器对 Worker 来源及 Blob 有约束，实际 CSP 的 worker-src 及回退规则可能限制创建；GM 权限不能被当成必然绕过此限制的保证。[Worker 构造器](https://developer.mozilla.org/en-US/docs/Web/API/Worker/Worker)、[worker-src](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Content-Security-Policy/worker-src)

Worker 创建失败须明确显示计算不可用，不把大规模模拟静默转到游戏主线程。确定性材料公式和现有收藏动作估算可继续按自身已验证能力工作，涉及缺失模拟结果的汇总保持未完整计算。终止 Worker、释放 Blob URL、移除监听及计时器都由应用 dispose 管理。

### DOM、焦点、样式与游戏交互

建议入口为 `mountPanel(root, services)`，返回更新数据和卸载接口。不要把整个 document 替换成代理对象来兼容旧代码。

- 所有查询以应用 root 为范围，元素通过 root.ownerDocument 创建；订单／价格弹窗也挂在同一 Shadow Root 内。
- 输入保留、草稿保护及恢复焦点读取 ShadowRoot.activeElement；document.activeElement 在边界外可能只是宿主。
- 事件委托绑定 root；需要跨边界识别时用 composedPath，处理事件重定向。只处理面板操作，不全局拦截游戏输入。[事件路径说明](https://developer.mozilla.org/en-US/docs/Web/API/Event/composedPath)
- 面板输入中的键盘事件需实测与游戏快捷键共存。外层捕获阶段的游戏监听不一定能靠 root 内 stopPropagation 阻止，不能声称 Shadow DOM 自动解决快捷键冲突。
- 模块全局状态改为实例状态；只挂载一个面板，折叠保留最新数据并暂停重计算／重绘，展开按最新数据恢复。

Shadow DOM 提供样式与 DOM 封装，不是独立 origin、独立 JS 运行环境或强安全边界；closed 模式也不提供这类保证。优先使用 open root，便于调试、验证和焦点处理。[Shadow DOM 文档](https://developer.mozilla.org/en-US/docs/Web/API/Web_components/Using_shadow_DOM)

### 存储与平台能力

订单、试配、价格、筛选及偏好使用独立命名空间的 GM 存储；不往游戏 origin 的 localStorage 写实验室存档。不假定新脚本能读取旧脚本 GM 数据，也不假定它能直接读取实验室网站 localStorage。[GM 存储文档](https://www.tampermonkey.net/documentation.php?locale=en&q=GM_values)

异步存储须先加载／校验再开放编辑，串行写入、合并待保存状态；失败保留有效内存并明确提示，不覆盖坏存档。角色实时捕获与订单写盘分开，不能每条世界消息都保存整份工作区。中英文站、角色、多标签页的隔离与并发规则要验证；角色稳定 ID 尚需核验，未核验前不得猜测账号归属。

公开行情先尝试无凭据 fetch；若目标域名环境需要 GM_xmlhttpRequest，则只连接固定公开市场地址，使用无凭据请求并保留原校验、超时和错误语义，不扩大为任意接口代理。GM_setClipboard 可适配复制；剪贴板读取仍需实际权限验证并提供文本／文件导入入口。[GM 网络接口](https://www.tampermonkey.net/documentation.php?locale=en&q=GM_xmlhttpRequest)、[剪贴板写入](https://www.tampermonkey.net/documentation.php?locale=en&q=GM_setClipboard)

## 游戏内面板视觉要求

视觉以真实游戏面板为基准，不沿用实验室的大页头、大属性卡和独立网站布局。功能结构可以适应复杂订单，但面板底色、字体字号、文字层级、边框、圆角、阴影、按钮、输入框、选中／禁用状态、表头、行高及间距应与游戏一致。

建议先选游戏内已有制造／仓库等面板作为参照，逐项测量，再维护一份小型主题变量和组件样式：

1. 从已核验的原生面板取得配色、字体及尺寸；可读取明确参照元素的 computed style 或已确认的 CSS 自定义属性。保留固定的已核验默认值，避免上游改类名后整面板失去样式。
2. 样式写入 Shadow Root；不直接依赖游戏压缩类名，也不整份复制游戏样式表。Shadow DOM 不会让游戏外部的普通选择器自动命中内部按钮、表格。
3. `:host` 设置必要主题变量、字体和颜色；对内部控件、box-sizing、表格、滚动区及弹窗明确设样式。继承属性与 CSS 变量仍需控制，不能把 attachShadow 当成完整样式重置。
4. 保留游戏习惯的关闭／折叠、标题栏、选中态和滚动表现。桌面可扩展面板宽度，窄屏使用游戏式紧凑布局；确保重要数量、状态和键盘焦点可读。
5. 语言、缩放、游戏已有主题切换（若实际存在）及窄屏下做并排截图检查。只响应已核验主题机制，不预设游戏一定存在明暗双主题。

本地 vendor 未包含已保存的游戏 CSS，本轮公开首页读取也未取得登录后的实际面板。因此不编造具体色值、字号或像素尺寸，不将实验室现有颜色称为游戏原生主题。本轮没有产出可声称已对齐的 UI 截图；样式采样和真实面板比较是实施前置验证。

## 配方选择面板与订单交互

配方选择面板增加“制造 / 收藏”切换，始终显示当前编辑订单。切换类型、技能或筛选不切换当前订单，也不清空另一类条目。

| 模式 | 候选与输入 | 加入当前订单 |
| --- | --- | --- |
| 制造 | 保留五技能、品质、搜索、分类及原有速率列；输入非负安全整数制造次数 | change 提交有效次数即加入／更新，零移除 |
| 收藏 | 保留现有九技能路线，区分采集／制造、品质、目标档、精通点及每点成本／时间筛选 | “加入订单”选择目标档，已选目标可增减档位或移除 |

收藏候选继续枚举支持的普通主产物路线，不缩减为五种制造技能。尚未取得收藏进度时明确等待同步，允许主动进入从零手动场景；未读取不当作零。自动同步后更新实际进度；库存不等于收藏计数，购买物品不能补收藏进度。

订单管理沿用新建、复制、命名、删除、编辑行高亮和整单执行选择。订单明细用“类型、物品／配方、品质、次数／目标、进度、估算／模拟状态、操作”表达两类任务；次数列只对制造行可编辑，收藏行操作目标档位。批量修改制造次数只作用于制造行，不把 100 次写成收藏 100 档。复制订单只复制意图和费用，不复制游戏进度或库存快照。

自动移除已完成选项仅针对收藏行；默认勾选，复用当前收藏行为，只在有效收藏进度更新后执行。保留未勾选执行的订单也有相同进度／完成判定。制造行不会因为仓库里已有成品就自动完成；空订单仍保留，至少有一张可编辑订单。旧收藏“清空配置保留计划”在新模型对应清空试配／角色数据而保留订单。

## 两类订单项与共同计算

建议存档使用有类型的条目，而不是复用同一个数字字段：

```js
{ kind: 'craft', jobId, tier, count }
{ kind: 'collection', itemId, jobId, target }
```

示例仅描述语义，非最终存档 schema。完整 schema 仍须版本号、订单 ID、名称、执行开关、加工费及严格校验。制造包含字符串即时升级配方 ID，收藏 jobId 当前为普通配方数字，校验不能强行统一。

### 语义与去重

- 制造 count 是要执行的次数。收藏 target 是累计收藏目标；缺口为 max(0, target−当前收藏计数)，不是制造次数。
- 目标缺口除以每次产量并向上取整，再考虑烧焦、品质和被捕概率，得到收藏预计执行次数。原收藏表“执行次数”实际显示目标数量缺口，新界面必须分成“还差产量”和“预计执行次数”。
- 同一订单同物品＋品质只保留一个收藏来源与最高目标；明确切换来源替换旧来源，不合并为两份目标。同制造配方＋品质按同一行更新次数，重复导入不能意外翻倍。
- 不同执行订单出现相同收藏物品＋品质时，建议标出执行冲突，要求把目标合并到一张订单或取消重复订单的执行勾选。当前收藏是同一角色共享进度，不能将每张订单从同一进度算出的奖励与材料直接相加，也不应擅自决定费用归属。冲突期间保留订单和各单独估算，执行总量标为未完整计算。
- 同一配方同时有制造次数与收藏目标时，两行表达独立任务，第一版不自动用制造预期产出抵扣收藏任务，不互相销行；材料按两项分别计算后汇总，并在相关行提示“另有同配方任务，尚未联合抵扣”。这是沿用独立任务口径的建议，不代表联合最省动作方案；未来若希望共享一次生产过程，需要另行设计执行顺序和产出归属。

### 材料、库存、报价和精通点

制造保持确定性材料需求；收藏使用当前纯动作期望材料需求。所选可计算条目按完整物品 ID 全精度相加，最后每种材料统一向上取整，再一次性扣除 bank＋pack。不得每张订单先扣库存或先向上取整，也不将预期产物当成已入库物品；普通与不同品质独立。

收藏备料高亮改为对所选执行订单的统一需求判断；不能让两个订单各自认领同一份材料。未知库存、冲突项、无法计算及数量超限不能当作零需求。收藏需求是期望备料，不能标成烧焦等随机机制的保证充足。

建议共用执行计划设一个明确的采购价格模式 global／ask／bid／vendor（默认 global），用于两类任务的采购表及比例加工费基数；缺价严格显示未知或明确的有效部分小计。现有制造利润使用的商人兜底估值保留来源说明，不把它冒充实际采购报价。这属于新项目的统一定价建议，实施时需先写入设计，不能直接改现有实验室全局价格规则。

收藏候选的每点成本仍按未抵库存的材料消耗估算；执行采购成本按共享库存抵扣后计算，两者不可混用。精通点只汇总有效、未重复的收藏目标；普通制造行不额外估算收藏奖励，也不把重叠目标奖励重复计算。批量产出跨越额外门槛继续按原收藏计算规则处理。

### 耗时与加工费

当前制造模拟含移动、回仓和成长；收藏 UI 的估算冻结当前属性，仅计算动作期望。新面板初版分别展示“制造模拟耗时”和“收藏动作期望”，不将两者包装成精确完成时间；采集多品质的联合产出优化仍未实现。

固定费每张非空执行订单只计一次；比例费按该订单材料消耗价值计算，不按抵库存后的购买金额计算。时间费沿用制造模拟耗时口径：纯制造订单保持原计算；包含未完成收藏项且设置了正的时间单价时，时间费及加工费总额明确为未完整计算，展示已知固定／比例分项。若用户希望按收藏纯动作期望计时间费，应另设明确模式并说明不含行程，而不能悄悄混用。包含无效项或缺报价时同样显示未知分项，不将其当零。

`collection-simulation.js` 目前只用于离线目标事件回归。第一版不直接把它变成所有收藏目标的在线模拟：这会增加计算负担，并改变当前收藏期望口径；若要统一真实行程模拟，需要单独核验性能与指标定义。

## 实时更新与计算调度

第一阶段仍建议“服务器有效快照到达即同步”。本地旧版源码已确认游戏会在服务器快照之间自行 tick 推进角色，旁听 welcome／snapshot 不能保证与界面逐刻一致；1199 当前客户端具体接入点本轮未重新审计，不将旧版压缩符号当稳定接口。

只读捕获必要字段：九技能角色配置、bank／pack、collections、公会和世界窗口。记录当前连接、单调序号、角色快照时间与 tick、世界数据时间及连接状态；公会／世界更新不得把旧角色库存重新标成新快照。新连接进入等待，不接受旧连接晚到结果，不向游戏发命令或新增游戏连接。

| 变化 | 影响 |
| --- | --- |
| 库存 | 更新共享材料抵扣、采购金额及备料高亮，不重启制造模拟、不改变收藏进度 |
| 收藏计数 | 重算目标缺口、精通点、收藏动作期望及材料；按开关移除已完成收藏行，不改变制造次数 |
| 参与计算的角色配置／有效增益 | 只使相关技能／配方的缓存失效；未变化的模拟不重启 |
| 行情／锁价 | 只重估费用和利润，不重新运行原始模拟 |
| 订单／筛选／面板开合 | 按实际影响更新；筛选不改变执行内容；折叠暂停计算及重绘 |

实时跟随与手动试配分开；用户输入草稿不会因更新丢失。收藏进度、库存与配置可分别维护 revision，Worker 结果带输入版本；连续更新采用仅保留最新任务的合并调度，确保能完成结果而不是无限终止重启。药剂／世界窗口到期需更新有效状态或显示过期，不能因没有新快照而一直标为生效。

## 迁移、实施顺序与验收

旧实验室制造工作区、收藏角色数据及收藏计划分别存储；新脚本不能跨 origin 自动读取。建议由旧站显式导出，再在新面板导入。制造订单转为 craft 行，旧收藏单计划转为一张“收藏计划”订单；接受旧 JSON 与 `DVILAB-PLAN:` 格式，但新混合订单使用新版本协议。导入前完整验证，成功后一次应用；失败、晚到结果或存档异常保留原数据。旧偏好能映射则保留，不能映射则明确提示，不静默丢弃。

同一工作区只能有一套有效角色配置；制造与收藏旧存档配置不一致时不能随导入顺序任意覆盖，建议只迁移订单意图，角色配置由当前游戏快照建立。滤器、旧自动移除偏好、锁价及采购模式需在迁移设计列明映射。面板验收前保留实验室 `/craft` 与 `/collection`，移除旧入口属于后续明确范围。

建议实施顺序：

1. 先做真实游戏载体验证：早期捕获、Shadow Root 样式、游戏面板样式采样、Blob Worker、GM 存储、公开行情和键盘焦点。Chromium／Firefox、两游戏域名及选定脚本管理器分别验证；失败明确报告，不自动退回 iframe 或主线程大模拟。
2. 建立独立项目与统一工作区，先迁移制造，再复用收藏模型和有类型订单项；共享一个 root、角色状态、价格服务和库存。
3. 接入制造／收藏候选切换、混合订单、执行聚合与冲突提示；分别核对原制造同输入同种子输出及原收藏估算输出，保留计算差异说明。
4. 接入实时推送和精确缓存失效，验证库存单独变化、收藏进度变化、同快照、旧连接晚到、断线、试配、折叠恢复及连续更新下的完成率。
5. 验证迁移、混合订单导入导出、存档错误、缺价／溢出、双语窄屏、游戏快捷键与原生面板截图对照，再执行独立发布验收。

必要业务用例包括：收藏进度 9→100 的缺口与奖励；一次多产物的次数换算；烧焦与采集品质概率；同单最高档替换；跨单收藏重复冲突；固定制造＋同配方收藏的独立任务提示；共享材料只扣一次；全精度合并后取整；未知库存与零库存区分；完成项移除不影响固定次数；混合耗时不伪装精确 ETA；固定费只计一次、比例费不受库存影响、收藏时间费未知。

本轮已执行相关设计与实现静态核对，并查阅上述官方文档。没有安装新脚本、执行游戏操作、构建新产物、运行功能测试、核验真实面板样式或做性能测量；历史测试通过不作为本轮结果。此前 curl 访问游戏因 DNS 解析失败，公开网页工具可读首页但未取得完整响应头和登录面板；当前 CSP、真实注入时机、Blob Worker、快照频率及主题细节仍未验证。原始资源归原游戏作者，公开可读不代表已获得开源或再分发许可。
